# HOT × NOWGO 데이터 아키텍처

운영 목표: 회원은 HOT에서 직접 가입하고 메뉴를 발견·제보하며, 확인된 점주는 NOWGO의 매장 페이지로 손님을 연결한다. HOT은 NOWGO와 회원 및 매장 권한 원천을 공유한다. 별도 비밀번호·회원 사본을 만들지 않는다.

## 데이터 원천

| 데이터 | 원천 | HOT에서 하는 일 |
| --- | --- | --- |
| 통합회원 ID·구글 로그인 | NOWGO 운영 Supabase `auth.users` | 같은 프로젝트의 OAuth로 가입·로그인하고 JWT를 서버에서 검증 |
| 점주 자격 | `owners`, `ng_business_verifications`, `ng_store_claims`, `stores` | 서버와 DB 함수에서 승인된 회원·매장·사업자 관계만 조회 |
| 메뉴 제보 | `hot_taste_observations` | 회원의 연락처, 점주의 사업자번호, 가격·주소·사진 경로를 행 단위 보안으로 저장 |
| 가입 동의 | `hot_member_consents` | 필수 안내 버전과 선택 이메일 수신 여부를 본인 계정에만 저장 |
| 저장 메뉴 | `hot_menu_saves` | 본인만 읽고 삭제 가능 |
| 제보 사진 | 비공개 Storage `hot-report-photos` | 2MB 이하 JPG/PNG/WebP. 회원·제보 ID를 이미지 자체에 추가하지 않음 |
| 공개 메뉴 | `hot_public_menus` 뷰 | `published_unverified`만 공개; 연락처·사업자번호·회원 ID는 제외 |

## 순환

1. 방문자가 프로모션에서 메뉴 지도로 이동해 검색·가격·맵기 필터를 사용한다. 가매장 세 곳은 예시로 표시한다.
2. 제보 또는 저장을 선택하면 HOT의 `/account/join`에서 NOWGO와 동일한 Supabase Auth 프로젝트로 구글 가입·로그인한다. 가입 후 필수 동의를 저장하고 원래 위치로 돌아온다. 다른 도메인 간 브라우저 세션 공유를 주장하지 않는다.
3. 고객은 연락처·가격·사진을 필수 제출한다. 서버가 JWT를 재검증하고 요청 필드를 검사한다. DB는 사용자 소유, 시간당 10건, 사진 객체 존재와 필수 동의를 다시 검사한 뒤 자동 공개한다. 수동 사전 승인 단계는 없다.
4. 공식 점주는 같은 계정으로 NOWGO에서 사업자·매장 권한 확인을 마친 뒤 HOT에서 소유 매장을 선택한다. DB가 승인 상태를 다시 조회한다. 확인된 매장에만 공식 점주 표시와 NOWGO `/p/{slug}` 링크를 제공한다. 권한이 철회되면 조회 시 공식 표시도 사라진다.
5. 매장 영업·품절은 NOWGO의 별도 확인 시각이 있는 API가 연결될 때만 표시한다. 현재 데이터가 없으면 `확인 필요`로 표시한다. 리뷰는 NOWGO 미니홈피에서 처리한다.

## 경계와 확장

- 공개 카드는 비공개 제보 테이블을 직접 조회하지 않고 제한된 뷰를 통한다. 사진 객체 이름은 무작위 제보 UUID이고, 비공개 버킷은 초안 소유자 업로드·삭제와 공개된 제보 사진 읽기만 허용한다.
- 공개 조회는 500건 단위 제한과 최근 순 인덱스가 있다. 이용자가 늘면 커서 기반 페이지네이션과 CDN 이미지 캐시를 추가한다. `GET /api/events`는 조회마다 DB에 쓰지 않는다. 업로드 제한과 DB 잠금 기반 작성률 제한은 동시 제출에도 적용된다.
- OAuth 허용 URL에 HOT callback을 등록해야 HOT 내 가입이 완료된다. 운영 환경 변수는 NOWGO 운영 프로젝트의 공개 URL·publishable 키만 사용한다. `service_role` 또는 사업자·연락처 값은 공개 클라이언트에 두지 않는다.
- 데이터베이스 변경은 `supabase/migrations/20260924*.sql`을 순서대로 적용한다. 개발 프로젝트에서 권한과 스키마를 검증한 뒤 운영에 적용한다. 도메인은 HOT Vercel 프로젝트의 GitHub `main` 배포를 따른다.
